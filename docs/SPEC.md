## 1. 무엇을 만드는가

사용자의 흐릿한 제품 아이디어를 **대화형 인터뷰**로 취조하여, **다른 AI(Claude Code 등)가 읽고 즉시 개발에 착수할 수 있는 PRD 문서**를 생성하는 로컬 우선 웹 앱.

**한 문장 정의:** PRD를 "쓰는" 도구가 아니라, PRD가 **완성되었는지 기계적으로 검증**하고 미완성이면 내보내기를 거부하는 도구.

### 이 앱이 존재하는 이유 (설계 판단의 근거)

선행 버전(프롬프트만으로 구현)은 실패했다. 실패 원인 4가지가 그대로 본 문서의 설계 원칙이 된다.

| 실패 현상 | 원인 | v3 대응 |
|---|---|---|
| 필수 섹션이 통째로 누락된 채 "완성" 출력 | 완성 판정을 LLM 자기 판단에 맡김 | **검증기를 코드로 구현** (§6) |
| 뒷 섹션일수록 내용이 부실해짐 | 긴 PRD를 1회 생성으로 뽑음 | **섹션 단위 누적 상태 + 결정적 조립** (§4) |
| 존재하지 않는 모델명·가격을 사실처럼 서술 | 미검증 정보에 표시 없음 | **고유명사 강제 태깅 + 검증기 차단** (§6.3) |
| 구현 불가능한 기능이 MVP에 통과 | 예산·환경 제약을 묻지 않음 | **S0 Builder Context를 인터뷰 1순위로** (§5.2) |

## 2. 설계 원칙 (타협 불가)

1. **상태는 앱이 소유한다. LLM은 상태를 기억하지 않는다.**
   PRD의 진실은 앱이 보관하는 JSON 객체 하나다. LLM에는 매 턴 그 JSON을 다시 넣어준다. "아까 확정했잖아"는 존재하지 않는다.

2. **LLM은 전체를 다시 쓰지 않는다. 패치만 반환한다.**
   매 턴 응답은 "어느 섹션을, 어떤 내용으로 갱신할지"의 연산 목록이다. 전문 재생성은 문서 부패의 주원인이므로 금지한다.

3. **최종 문서는 생성이 아니라 조립이다.**
   완성된 상태 JSON을 템플릿에 렌더링한다. LLM이 마지막에 PRD를 통째로 쓰게 하지 않는다.

4. **검증기가 최종 판단자다.**
   내보내기 버튼은 검증기가 통과시킬 때만 활성화된다. LLM이 "완성되었습니다"라고 말해도 검증기가 거부하면 미완성이다.

5. **모르는 것은 모른다고 표시한다.**
   외부 서비스명·모델명·가격·성능 수치는 검색으로 확인하지 않았다면 `[미검증]` 태그를 붙인다. 태그 없는 고유명사가 있으면 검증기가 잡는다.

## 3. MVP 범위

### In Scope
- 대화형 인터뷰 UI (좌: 채팅 / 우: PRD 실시간 미리보기)
- PRD 상태 JSON 관리 및 브라우저 영속화
- LLM 패치 기반 섹션 갱신
- 코드 기반 완성도 검증기
- 최종 PRD 마크다운 내보내기 + **Claude Code용 압축 프롬프트** + **개발 환경·에이전트 세팅 지침** 동시 생성
- BYOK (사용자가 자기 API 키 입력)

### Out of Scope — v2+ 백로그
| 항목 | 미룬 이유 |
|---|---|
| 회원가입·인증·서버 DB | MVP 사용자는 빌더 본인. 서버 없으면 유출 사고도 없음 |
| 결제·구독 | 사용자 1명에게 과금할 수 없음 |
| 웹 검색 연동(시장 조사) | 검증 파이프라인이 먼저 안정화돼야 함. MVP는 `[미검증]` 태깅으로 대체 |
| 다중 프로젝트 관리 | 단일 프로젝트 1개로 시작. 리스트 UI는 나중 |
| 음성 입력 | 부가 기능 |
| PRD 버전 diff/머지 | 상태 스키마 확정 후 |

## 4. 데이터 모델 — 이 앱의 핵심

### 4.1 PRD 상태 객체

```typescript
type SectionId = 'S0'|'S1'|'S2'|'S3'|'S4'|'S5'|'S6'|'S7'|'S8'|'S9'|'S10'|'S11';

type SectionStatus = 'empty' | 'drafting' | 'confirmed';

interface Section {
  id: SectionId;
  title: string;
  required: boolean;
  status: SectionStatus;
  content: string;          // 마크다운. 이것이 최종 문서에 그대로 들어감
  updatedAtTurn: number;
  locked: boolean;          // 사용자가 직접 편집(FR-007)하면 true. 엔진의 set_section을 거부한다
}

interface Requirement {
  id: string;               // "FR-001" | "NFR-001"
  title: string;
  description: string;
  acceptanceCriteria: string[];   // 최소 2개. 검증 가능한 문장만
  priority: 'Must' | 'Should' | 'Could';
  dependsOn: string[];
  section: 'FR' | 'NFR';
}

interface CostLine {
  item: string;             // "LLM 호출 (인터뷰 1세션)"
  unit: string;             // "세션당"
  estimatedCost: number;    // USD
  verified: boolean;        // 실제 가격표 확인 여부
  note: string;
}

interface PRDState {
  schemaVersion: number;    // 영속화 마이그레이션 기준점. 현재 1
  projectName: string;
  version: string;
  turn: number;
  sections: Record<SectionId, Section>;
  requirements: Requirement[];
  costModel: CostLine[];          // 수익화 섹션(S9)이 있으면 필수
  openQuestions: string[];        // 최소 5개 필요
  assumptions: { text: string; source: 'user' | 'default' | 'inferred' }[];
  unverifiedTerms: string[];      // [미검증] 태그가 붙은 고유명사 수집
  history: { turn: number; role: 'user'|'engine'; text: string }[];
}
```

### 4.2 섹션 정의

| ID | 섹션 | 필수 | 비고 |
|---|---|---|---|
| S0 | Builder Context | ★ | **인터뷰 최초 수집.** 예산/보유 키/배포 환경/가용 시간 |
| S1 | Project Overview | ★ | 한 문단 정의, 타깃, 핵심 가치 |
| S2 | MVP Scope (In) | ★ | |
| S3 | Out of Scope | ★ | 항목마다 미룬 사유 1줄 |
| S4 | User Stories & Flow | ★ | |
| S5 | Functional Requirements | ★ | `requirements[]`에서 렌더링 |
| S6 | Non-Functional Requirements | ★ | 보안/개인정보/성능/에러처리 4개 축 모두 |
| S7 | Edge Cases & Failure Scenarios | ★ | 최소 5개 |
| S8 | Tech Stack & Constraints | ★ | 확정 제약 / `Suggestion:` 구분 |
| S9 | Cost & Monetization | 조건부 | 수익 모델 언급 시 ★. `costModel` 필수 |
| S10 | Open Questions & Assumptions | ★ | |
| S11 | Deployment & Operations | ★ | 배포처, 환경변수, 로깅, 백업 |

> **주의:** S9는 "수익화 계획이 있으면 원가 표가 반드시 있어야 한다"는 조건부 필수다. 원가 없는 요금제는 검증기가 차단한다.

## 5. LLM 호출 계약

### 5.1 요청 구성

매 턴 다음을 조립해 1회 호출한다.

```
[시스템 지침 — §5.2]
[현재 PRD 상태 JSON — sections의 content 포함 전문]
[직전 대화 6턴]
[사용자 최신 입력]
```

**중요:** `history` 전체를 넣지 않는다. 상태 JSON에 이미 확정 내용이 들어있으므로 대화 원문은 최근 것만 있으면 된다. 이것이 컨텍스트 유실을 막는 구조다.

### 5.2 엔진 시스템 지침 (앱에 내장할 프롬프트)

```
당신은 냉정한 시니어 프로덕트 매니저다. 사용자의 아이디어를 취조하여
다른 AI가 읽고 즉시 개발할 수 있는 PRD를 완성시킨다.

# 절대 규칙
1. 확정되지 않은 외부 정보(서비스명, 모델명, 가격, 성능 수치)를 사실처럼
   쓰지 않는다. 반드시 [미검증] 태그를 붙인다.
2. 한 턴에 질문은 최대 3개. **선택지가 있는 질문은 questions 배열로 낸다**(FR-014).
   보기마다 장단점을 함께 적고, 권장안이 있으면 표시한다. 사용자는 보기를 고르거나
   주관식으로 답할 수 있다.
3. 사용자가 질문과 무관한 이야기를 해도 버리지 않는다. 관련 섹션에 반영하고
   "말씀하신 X는 S___에 반영했습니다"라고 알린다.
4. 아첨하지 않는다. 매 턴 최소 1개는 아이디어의 약점이나 위험을 지적한다.
   단, 대안을 함께 제시한다.
5. 구현 방법의 최종 결정권은 이 문서를 받을 개발 AI에 있다. 기술 선택은
   "Suggestion:" 접두어로만 쓴다. 단 예산·보유 키·배포 환경은 제약이며
   개발 AI가 바꿀 수 없다.
6. `locked: true`인 섹션은 사용자가 직접 편집한 것이다. set_section 패치를
   보내지 않는다. 그 섹션에 변경이 필요하면 reply에서 사용자에게 잠금 해제를
   요청한다.

# 인터뷰 순서 (강제)
1단계 S0 — 예산, 보유 API 키, 배포 환경, 가용 시간을 먼저 확정한다.
        이것 없이 기능 논의로 넘어가지 않는다. 예산이 범위를 결정한다.
2단계 S2/S3 — 만들 것과 안 만들 것을 강제 분리한다.
        사용자가 기능을 추가하려 하면: "MVP에 넣으면 [예상 영향]만큼 늦어집니다.
        S3 백로그에 두고 v2에서 논의하는 것을 제안합니다. 그래도 넣으시겠습니까?"
3단계 나머지 섹션을 우선순위대로 채운다.
4단계 압박 검증 — 악용 시나리오, 개인정보, 비용이 선형 이상 증가하는 지점,
        경쟁사가 복제하면 무엇이 남는가.

# 스코프 상한 (초과 시 사용자에게 경고하고 S3로 이관 제안)
- MVP 기능 요구사항(FR) 12개 초과
- S0에서 확인한 예산으로 감당 불가한 원가 구조
- 선례가 확인되지 않은 기술이 3개 이상

# 출력 형식
반드시 아래 JSON만 출력한다. 앞뒤에 설명이나 코드펜스를 붙이지 않는다.

{
  "reply": "사용자에게 보여줄 메시지. 반영 사항 → 지적 → 질문 순서.",
  "patches": [
    {"op": "set_section", "id": "S1", "content": "마크다운 전문", "status": "confirmed"},
    {"op": "add_requirement", "requirement": { ...Requirement 스키마... }},
    {"op": "add_open_question", "text": "..."},
    {"op": "add_cost_line", "line": { ...CostLine 스키마... }},
    {"op": "add_unverified", "term": "..."}
  ],
  "nextFocus": "S4"
}
```

### 5.3 응답 처리

- JSON 파싱 실패 시 코드펜스 제거 후 1회 재시도. 그래도 실패하면 **모델에게 "직전 응답이 JSON 스키마를 위반했다. 스키마만 지켜 다시 출력하라"**로 재요청 (최대 2회).
- `set_section`은 해당 섹션 content를 **교체**한다. 이어붙이지 않는다.
- 모든 패치 적용 후 상태를 저장하고 검증기를 재실행한다.

## 6. 검증기 — 코드로 구현할 것

> LLM에게 검증을 시키지 않는다. 순수 함수로 구현하고 단위 테스트를 붙인다.

```typescript
interface ValidationIssue {
  severity: 'block' | 'warn';
  code: string;
  message: string;
  sectionId?: SectionId;
}

function validate(state: PRDState): ValidationIssue[]
```

### 6.1 차단 규칙 (하나라도 걸리면 내보내기 불가)

| 코드 | 조건 |
|---|---|
| `MISSING_SECTION` | 필수 섹션 중 `status !== 'confirmed'` 또는 content 200자 미만 |
| `NO_FR` | `requirements` 중 section='FR'이 3개 미만 |
| `FR_NO_AC` | AC가 2개 미만인 FR 존재 |
| `AC_NOT_TESTABLE` | AC 문장에 측정 가능 요소(숫자/조건/관찰가능 동작)가 없음 — §6.2 |
| `NO_NFR` | NFR이 4개 미만 (보안/개인정보/성능/에러처리) |
| `FEW_EDGE_CASES` | S7 항목이 5개 미만 |
| `FEW_OPEN_QUESTIONS` | `openQuestions` 5개 미만 |
| `MONETIZATION_NO_COST` | S9에 가격/요금제 언급이 있으나 `costModel`이 비어 있음 |
| `UNTAGGED_PROPER_NOUN` | 알려진 벤더/모델 사전에 매칭되는 고유명사가 `[미검증]` 없이 등장 — §6.3 |
| `BUDGET_OVERRUN` | `costModel` 합계가 S0 예산 상한 초과 |

### 6.2 AC 검증 (`AC_NOT_TESTABLE`)

다음 중 최소 1개를 포함해야 통과:
- 숫자 + 단위 (`3초 이내`, `100건`)
- 조건절 (`~하면`, `~일 때`, `~인 경우`)
- 관찰 가능 동작 (`표시된다`, `저장된다`, `차단된다`, `반환한다`)

**차단 대상 예시:** "사용자 경험을 극대화한다", "안정적으로 동작한다", "직관적인 UI를 제공한다"

### 6.3 미검증 고유명사 탐지

`src/validator/vendorDict.ts`에 벤더/제품 키워드 사전을 둔다.
(예: `openai`, `gpt`, `claude`, `gemini`, `grok`, `llama`, `vercel`, `supabase`, `elevenlabs` 등 + 버전 패턴 `/\b[a-z]+[-\s]?\d+(\.\d+)?\b/i`)

섹션 content에서 사전 매칭 시, 같은 문장에 `[미검증]` 또는 출처 URL이 없으면 `UNTAGGED_PROPER_NOUN` 발생.

> **사전은 완전할 필요 없다.** 목적은 완벽한 탐지가 아니라 "가격·모델명을 무심코 확정 서술하는 습관"의 차단이다.

### 6.4 경고 규칙 (내보내기는 허용, UI에 노란 배지)

- FR 12개 초과
- `assumptions` 중 `source: 'inferred'`가 5개 초과
- 특정 섹션이 20턴 이상 `empty` 유지

## 7. 기능 요구사항

### FR-001: 대화형 인터뷰 세션
- **설명:** 사용자가 아이디어를 입력하면 엔진이 인터뷰를 시작하고 턴을 이어간다.
- **AC:**
  - [ ] 사용자 메시지 전송 시 로딩 표시가 나타나고, 응답 수신 후 채팅에 렌더링된다
  - [ ] 엔진 응답의 `reply` 필드만 채팅에 표시되고 `patches`는 표시되지 않는다
  - [ ] 첫 턴에서 엔진이 S0(예산/보유 키/배포 환경) 질문을 먼저 던진다
- **우선순위:** Must

### FR-002: 상태 기반 컨텍스트 조립
- **설명:** 매 호출 시 상태 JSON 전문 + 최근 6턴만 전송한다.

  - [ ] 상태 JSON의 모든 confirmed 섹션 content가 프롬프트에 포함된다
  - [ ] 30턴 이상 진행 후에도 초반 확정 섹션의 내용이 유실되지 않는다 (테스트 필수)
- **우선순위:** Must
- **의존성:** FR-001

### FR-003: 패치 적용 엔진
- **설명:** LLM이 반환한 patch 연산을 상태에 적용한다.

  - [ ] 알 수 없는 `op` 값은 무시하고 콘솔에 경고를 남긴다 (앱이 죽지 않는다)

### FR-014: 객관식 질문 카드
- **설명:** 엔진의 질문을 산문이 아니라 **선택지가 붙은 카드**로 제시한다. 사용자는 보기를 클릭해 답하고, 필요하면 주관식 칸에 부연한다.
- **설명 보강:** 산문 질문은 사용자가 전부 타이핑해야 해서 답이 짧아지고 누락된다. 선택지에 장단점을 나란히 적으면 §5.2 절대규칙 4(약점 지적)가 선택 시점에 자연스럽게 전달된다.
- **AC:**
  - [ ] 한 턴에 질문 카드가 최대 3개 표시되고, 답한 개수가 `n/3` 형태로 보인다
  - [ ] 각 보기에 한 줄 제목과 장단점 설명이 함께 표시된다
  - [ ] 엔진이 권장하는 보기에 표시가 붙는다
  - [ ] 질문마다 선택과 무관하게 주관식 의견을 덧붙일 수 있다
  - [ ] 답하지 않고 자유 입력만으로 진행할 수 있다 (카드는 강제가 아니다)
  - [ ] 제출 시 선택과 주관식이 하나의 사용자 입력으로 조립되어 엔진에 전달된다
- **우선순위:** Must
- **의존성:** FR-001
- **비고:** 총 14개로 §6.4 경고선(12개)을 2개 초과한다. 빌더 승인 2026-08-27. 근거: 실사용에서 산문 질문의 답변 부담이 확인됨.

### FR-013: 개발 환경·에이전트 세팅 지침 생성
- **설명:** 내보내기 시 PRD 본문·압축 프롬프트와 함께, **이 프로젝트를 Claude Code에서 어떻게 세팅하고 시작할지**를 적은 지침을 생성한다.
- **설명 보강:** PRD를 받아도 "그래서 뭘 먼저 만들지, 컨텍스트는 어떻게 관리할지"가 없으면 바이브코딩이 산만해진다. 이 지침이 그 공백을 메운다. 내용은 상태 JSON에서 결정적으로 조립하며 LLM이 새로 쓰지 않는다.
- **포함 항목:**
  - `CLAUDE.md` 초안 — 프로젝트 한 줄 정의, 타협 불가 원칙, Out of Scope("구현 금지" 목록), 확정 제약
  - 문서 배치 — 긴 스펙을 `docs/`로 분리하고 진행 상황 파일을 두는 구조
  - 서브에이전트 제안 — 스펙 조회용, 테스트 실행용 등 이 프로젝트에 맞는 것만
  - 개발 순서 — FR 의존성 그래프에서 유도한 마일스톤. 검증 가능한 것부터
  - 권한 allowlist 후보 — S8 기술 스택에서 유도 (예: Vite면 `npm run`, `npx vitest`)
- **AC:**
  - [ ] `CLAUDE.md` 초안에 S3(Out of Scope) 항목이 "구현 금지" 목록으로 들어간다
  - [ ] 개발 순서가 FR의 `dependsOn`을 위반하지 않는다
  - [ ] 지침이 LLM 재생성이 아닌 상태 JSON의 결정적 렌더링이다
  - [ ] 전체본·압축본·세팅 지침을 각각 별도 버튼으로 복사할 수 있다
- **우선순위:** Should
- **의존성:** FR-008
- **비고:** 이 FR로 총 13개가 되어 §6.4 경고 규칙(FR 12개 초과)을 의도적으로 초과한다. 빌더 승인 2026-08-27.

## 8. 비기능 요구사항

- **NFR-001 (보안):** API 키는 서버로 전송하지 않는다. 서버 컴포넌트를 두는 경우에도 키는 클라이언트 보관 후 요청 시 헤더로만 전달한다. 키를 로그에 남기지 않는다.
- **NFR-002 (개인정보):** MVP는 서버 저장소를 두지 않는다. 모든 데이터는 사용자 브라우저에 있다. 이 사실을 첫 진입 시 1회 고지한다.
- **NFR-003 (성능):** LLM 응답 대기 중 UI가 멈추지 않는다. 스트리밍이 가능하면 `reply` 필드만 스트리밍하고 `patches`는 완료 후 일괄 적용한다.
- **NFR-004 (에러 처리):** 네트워크 실패, 401(키 오류), 429(레이트 리밋), 스키마 위반을 각각 구분해 사용자에게 다른 메시지를 보여준다. 어떤 경우에도 진행 중 상태를 잃지 않는다.
- **NFR-005 (테스트):** 검증기(§6)와 패치 적용기(FR-003)는 단위 테스트 필수. UI 테스트는 MVP 범위 외.

## 9. 기술 스택

**확정 제약 (변경 불가)**
- 서버 DB 없음. 클라이언트 영속화만.
- API 키는 사용자 소유(BYOK). 앱에 키를 내장하지 않는다.
- 단일 개발자, 소규모 코드베이스 유지.

**Suggestion (개발 AI 재량으로 변경 가능, 변경 시 사유 기록)**
- `Suggestion:` React + Vite + TypeScript. Next.js는 서버가 필요 없는 구조에 과함.
- `Suggestion:` Tailwind CSS.
- `Suggestion:` 상태 관리는 Zustand 또는 useReducer. Redux는 과함.
- `Suggestion:` 영속화는 IndexedDB(idb-keyval). localStorage는 상태 JSON이 커지면 한계.
- `Suggestion:` 마크다운 렌더링은 react-markdown.

**엔진용 LLM 선정 지침 (착수 시점에 확인할 것)**
- 이 앱의 인터뷰 품질은 모델 성능에 직결된다. 저가·고속 모델은 지침 준수율이 낮아 선행 버전 실패의 원인이 되었다.
- 인터뷰 턴에는 **지침 준수와 JSON 스키마 안정성이 높은 중상급 모델**을 사용한다.
- 구체 모델명과 단가는 `[미검증]`이다. **개발 착수 시 벤더 공식 문서에서 현재 사용 가능한 모델과 가격을 확인한 뒤 `config.ts`에 기입한다.** 본 문서에 특정 모델명을 하드코딩하지 않은 것은 의도적이다.
- **엔진 모델은 `gemini-3.7-flash` 하나로 확정한다** (빌더 확정 2026-08-27). Anthropic 안은 철회.
  - 모델 ID는 **Models API로 직접 확인했다**(2026-08-27). 추측이 아니다. `gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.1-flash-lite`도 실재한다.
  - **Pro 티어는 `gemini-3.1-pro-preview` 프리뷰만 존재한다.** 프리뷰는 예고 없이 바뀌거나 사라질 수 있어 앱이 의존하지 않는다. 정식 승격 시 재검토.
  - 단가는 `[미검증]` — 빌더 제공 자료 기준 $0.75 / $3.75 per 1M. **2027-01-01에 2배 인상 예정**이라는 caveat이 있다. M3 착수 시 aistudio.google.com/pricing 확인 후 `config.ts`에 기입.
- 모델 ID·단가는 `config.ts` 한 곳에만 둔다. 교체 시 그 파일만 고친다.
- **JSON 강제는 `responseMimeType: "application/json"` + `responseSchema`로 한다.** 실측 검증 완료(2026-08-27):
  - `id`·`nextFocus`에 **SectionId enum을 반드시 넣는다.** 없으면 모델이 `"overview"`, `"problem_definition_and_target_audience"` 같은 어휘를 지어낸다.
  - **op별로 배열을 분리한다** (`setSections` / `addOpenQuestions` / `addUnverified` / …). Gemini `responseSchema`는 `oneOf` 판별 유니온을 지원하지 않아, 단일 `patches` 배열로는 op별 필수 필드를 강제할 수 없다(`set_section`인데 `content` 대신 `text`를 채우는 현상 확인).
  - 어댑터가 이 벤더 고유 형식을 §5.2의 정규 `Patch[]`로 변환한다. **앱 내부 계약은 §5.2 그대로다.**
- **thinking 토큰이 출력 토큰으로 청구된다.** 무제한이면 출력의 85%가 thinking이었다(300/354). `thinkingConfig.thinkingBudget`으로 통제한다 — 512 설정 시 92토큰으로 감소, 품질 저하 없음.
- LLM 호출은 어댑터 뒤에 격리한다. UI는 `callEngine(state, input)` 하나만 안다. 나중에 벤더를 늘리거나 서버 프록시로 옮길 때 어댑터만 교체된다.
- **런타임 패치 가드(M2 `isPatch`)는 스키마 강제와 별개로 유지한다.** 스키마가 있어도 모델이 규약을 벗어나는 것이 실측으로 확인됐다.

## 11. 엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| LLM이 JSON 대신 산문 반환 | 재시도 2회 → 실패 시 상태 보존하고 사용자에게 재시도 요청 |
| 패치에 존재하지 않는 섹션 ID | 무시 + 콘솔 경고. 앱 정상 동작 |
| 사용자가 첫 턴부터 "알아서 다 만들어줘" | S0 질문을 먼저 던지고, 답을 거부하면 기본값을 제안한 뒤 assumptions에 `source:'default'`로 기록 |
| 사용자 답변이 주제에서 크게 이탈 | 관련 섹션에 반영 후 "X는 S__에 반영했습니다" 피드백. 버리지 않음 |
| 40턴 초과 | 경고 배지 + 미확정 필수 섹션만 집중 질문하도록 nextFocus 강제 |
| API 키 무효(401) | 설정 화면으로 유도. 진행 상태 유지 |
| 429 레이트 리밋 | 지수 백오프 3회 재시도 후 사용자 안내 |
| 새로고침/탭 종료 | 마지막 저장 지점에서 복구 |
| 상태 JSON이 컨텍스트 한계 근접 | 가장 오래된 history부터 제거(섹션 content는 절대 제거 금지) |

## 12. 개발 순서

> Claude Code는 아래 순서대로 진행하고, 각 단계 완료 시 사용자에게 확인받은 뒤 다음으로 넘어간다.

1. **M1 — 타입과 검증기.** `PRDState` 타입 정의 + `validate()` 구현 + 단위 테스트. **UI보다 먼저.** 이 앱의 본질이 검증기이므로 여기가 먼저 서야 한다.
2. **M2 — 패치 엔진.** `applyPatches()` + 테스트. LLM 없이 목업 패치로 검증.
3. **M3 — LLM 연동.** 프롬프트 조립, 호출, 파싱, 재시도. 단일 턴 왕복 성공까지.
4. **M4 — UI 셸.** 채팅 + 미리보기 2단 레이아웃, 검증 이슈 패널.
5. **M5 — 영속화 + BYOK 설정 화면.**
6. **M6 — 내보내기.** 전체본 렌더러 + 압축본 렌더러.
7. **M7 — 실사용 검증.** 이 문서에 적힌 앱 자체를 이 앱으로 다시 기획해본다. 30턴 이상 돌려 컨텍스트 유실과 검증기 오탐을 잡는다.

## 14. Handoff Note (Claude Code에게)

- 본 문서의 **FR/NFR ID를 작업 추적 단위**로 사용할 것. 커밋 메시지에 ID를 남길 것.
- **§3 Out of Scope 항목은 구현하지 말 것.** 인증, 서버 DB, 결제, 웹 검색 연동은 이번 범위가 아니다. 좋은 아이디어라도 추가하지 말 것.
- §9의 `Suggestion:` 항목은 재량으로 변경 가능하나, **변경 시 사유를 기록**할 것. `Suggestion:` 없는 항목은 제약이므로 변경 금지.
- §13 Open Questions는 해당 코드 작성 **직전에** 사용자에게 확인할 것. 임의 결정하지 말 것.
- **모델명·가격·API 스펙을 기억에 의존해 코드에 쓰지 말 것.** 반드시 공식 문서를 확인하고, 확인 불가하면 `config.ts`에 `TODO: 확인 필요` 주석과 함께 남기고 사용자에게 알릴 것.
- §0 `[BUILDER_CONTEXT]`가 비어 있으면 코드 작성 전에 사용자에게 먼저 물을 것.
- 본 문서 수정이 필요하면 임의로 고치지 말고 변경 요청을 사용자에게 제시할 것.
