## 배경

빌더 요청 2건:

1. 4~6개 벤더의 최신·최고 성능 모델을 원칙으로 지원하되, **가격을 보고 사용자가 모델을 낮춰 선택**할 수 있어야 한다. (예: Fable 5 대신 Opus 5)
2. 각 모델을 **켜고 끌 수 있어야** 한다.
3. MVP 자가 검증 후 **상품성이 있으면 유료 서비스로 전환**을 염두에 둔다.

## A1 — FR-013 신설: 벤더/모델 레지스트리 및 선택

### 설명

`config.ts`에 벤더·모델 레지스트리를 두고, 설정 화면에서 사용자가 벤더별로 모델을 켜고 끄고 하나를 엔진으로 선택한다. 각 항목에 단가와 세션당 추정 비용, 검증 상태를 표시한다.

### 타입

```typescript
type VendorId = 'anthropic' | 'openai' | 'google' | 'xai' | 'openweight';
type Tier = 'frontier' | 'balanced' | 'budget';

interface ModelEntry {
  id: string;              // API에 그대로 넣는 모델 ID
  vendor: VendorId;
  label: string;
  tier: Tier;
  inputPer1M: number;      // USD
  outputPer1M: number;     // USD
  enabled: boolean;        // 사용자가 켜고 끄는 값
  verified: boolean;       // 벤더 공식 가격표를 직접 확인했는가
  checkedAt: string | null;// 'YYYY-MM-DD'
  sourceUrl: string | null;
  caveat: string | null;   // 프로모션 만료, 장문 미터 전환 등
}
```

### AC

- [ ] `verified: false`인 모델은 가격 옆에 `[미검증]` 배지가 표시된다
- [ ] `caveat`가 있으면 모델 선택 시 경고 문구가 1회 노출된다
- [ ] `enabled: false`인 모델은 선택 목록에 나타나지 않는다
- [ ] 선택한 모델 ID가 `PRDState`에 저장되고 S0 섹션 렌더링에 포함된다
- [ ] 세션 도중 모델을 교체해도 진행 중 상태가 유실되지 않는다
- [ ] 벤더를 추가할 때 `config.ts` 레지스트리 한 곳만 수정하면 된다 (어댑터 제외)

**우선순위:** Must · **의존성:** FR-011(BYOK)

> ⚠ **스펙 §6.4 경고 규칙 발동.** FR이 12개를 넘으면 경고 배지 대상이다. FR-013 추가로 13개가 되므로,
> 이 앱을 이 앱으로 기획했다면 검증기가 노란 배지를 띄웠을 상황이다. 의도된 초과임을 여기 기록한다.

## A3 — 유료 서비스 전환 대비

빌더 의도: MVP 자가 검증 → 상품성 확인 시 외부 고객 유료 결제.

**스펙과 충돌하지 않는다.** §3이 인증·서버DB·결제를 "v2+ 백로그"로 분류했지 영구 제외가 아니다. MVP 범위는 그대로 간다.

### MVP에서 하지 않을 것 (§14 준수)

회원가입, 인증, 서버 DB, 결제, 구독, 사용량 과금. **좋은 아이디어여도 추가하지 않는다.**

### MVP에서 해둘 것 — 나중 전환 비용을 낮추는 3가지

1. **LLM 호출을 어댑터 뒤에 격리한다.** `callEngine(state, input): Promise<EngineResponse>` 하나만 UI가 알게 한다. 클라이언트 직접 호출 → 서버 프록시 전환 시 어댑터만 교체된다.
2. **`PRDState`에 `schemaVersion` 필드를 둔다.** 나중에 서버 DB로 옮길 때 마이그레이션 기준점이 된다.
3. **FR-012 토큰/비용 계측을 처음부터 정확히 쌓는다.** 나중에 과금 미터의 기반이 된다. 우선순위를 Should → **Must**로 올릴 것을 제안한다.

> **전환의 진짜 난점:** BYOK와 유료 SaaS는 신뢰·과금 모델이 정반대다. 외부 고객은 자기 키를 넣지 않으므로 서버 보관 키 + 사용량 계측 + 남용 방지가 전부 필요해진다. 위 3가지는 그 전환을 **싸게** 만들 뿐, 없애주지 않는다. v2 착수 시 별도 기획이 필요하다.

## A5 — 프롬프트 캐싱 (앞선 판단 정정)

이전에 "이 앱에서 캐싱 효과가 미미하다"고 했으나 **과소평가였다.**

캐시는 프리픽스 정확 일치로 동작하고, 렌더 순서는 `tools → system → messages`다. 상태 JSON이 매 턴 바뀌는 건 맞지만, **섹션이 S0→S11 순서로 채워지므로 앞쪽 섹션이 먼저 안정화된다.** 섹션 직렬화 순서를 고정하고 확정된 앞 섹션 뒤에 캐시 브레이크포인트를 두면, 그 앞부분은 히트한다.

- 시스템 프롬프트(§5.2, 약 1K 토큰) — 항상 캐시 가능
- 확정된 앞쪽 섹션들 — 인터뷰가 진행될수록 캐시 가능 구간이 늘어남
- 제약: 요청당 브레이크포인트 최대 4개, 최소 캐시 프리픽스 약 1024 토큰

**단, 이건 벤더마다 다르다.** Anthropic 캐시 히트가 입력가 10%라는 건 검증됐지만 다른 벤더의 캐시 정책은 `[미검증]`이다. M3에서 어댑터별로 확인한다.
