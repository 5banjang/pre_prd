## A — 타협 불가 원칙 4 개정 ⚠️ 이 개정안의 핵심

### 현행

> 4. **검증기가 최종 판단자**다. LLM이 "완성"이라 해도 검증기가 거부하면 미완성.

### 개정안

> 4. **검증기가 최종 판단자**다. LLM이 "완성"이라 해도 검증기가 미완성이라 하면 미완성이다.
>    다만 그 판단의 결과는 **차단이 아니라 고지**다. 검증기는 무엇이 비었는지 내보내기 직전에
>    사용자에게 전부 보여주고, **뽑을지 말지는 사용자가 정한다.**
>    대신 **건너뛴 항목은 산출물에 반드시 남는다.** 조용히 사라지지 않는다.

### 왜 이렇게 쓰는가

빌더 지시는 "**문서가 안 나오게 하지 말라**"이지 "**검증을 하지 말라**"가 아니다.
오히려 5번 지시("미완성 항목을 화면에 명시")는 검증기를 **더 잘 보이게** 하라는 요구다.
따라서 검증기는 약해지지 않는다. **역할이 문지기에서 점검표로 바뀐다.**

지켜야 할 선 하나: 건너뛴 항목이 문서에서 **사라지면 안 된다.**
개발 AI가 "이 부분은 미정"임을 모르고 임의로 채우면 이 앱의 존재 이유가 없어진다.
`renderDraftBanner()`가 이미 그 일을 하고 있으므로 이를 정식 경로로 승격한다.

### 코드 영향

- `canExport()` 폐기. 내보내기는 **항상 가능**하다.
- `ValidationIssue.severity`의 `'block'`을 `'incomplete'`로 개명한다. 의미가 바뀌었으므로 이름도 바꾼다.
- 검증 규칙 13종과 테스트 174개는 **그대로 유지**한다. 판정 로직은 하나도 안 버린다.
- 산출물에는 항상 미완성 목록이 붙는다 — 통과 시에는 "전 항목 통과" 한 줄로.

## B1 — FR-015 신설: 자료 첨부와 1회 추출

> **우선순위:** Must · **의존:** FR-002 · **서버 불필요**

### 설계 원칙 — 원본을 컨텍스트에 남기지 않는다

첨부를 대화 컨텍스트에 계속 실으면 **매 턴 재전송되어 비용이 턴 수에 비례해 폭증**한다.
1시간 녹음을 컨텍스트에 둔 채 30턴을 돌면 $0.086이 아니라 **$2.6**이다.

```
첨부 → 1회 추출 호출 → 섹션 패치 + Assumption 등록 → 원본 폐기
```

이는 타협 불가 원칙 1(**상태는 앱이 소유. LLM은 기억하지 않는다**)과 같은 구조다.
원본은 상태에 들어가지 않고 추출된 **텍스트만** `PRDState`에 남는다.

### 타입 추가 (§4)

```typescript
export type AttachmentKind = 'document' | 'audio' | 'link';

export interface AttachmentRecord {
  id: string;
  kind: AttachmentKind;
  /** 파일명 또는 URL. 원본 바이트는 저장하지 않는다. */
  name: string;
  bytes: number | null;
  extractedAtTurn: number;
  /** 이 첨부 1건이 쓴 토큰 — FR-012 누적에 합산 */
  tokensUsed: number;
  /** 엔진이 요약한 한 문단. 원문이 아니다. */
  summary: string;
  touchedSections: SectionId[];
}
```

`PRDState`에 `attachments: AttachmentRecord[]` 추가. **원본 바이트는 어디에도 저장하지 않는다.**

### 추출 결과의 신뢰도

첨부에서 도출된 내용은 사용자가 직접 말한 것이 아니다.

- 첨부 기반 가정은 전부 `Assumption { source: 'inferred' }`로 등록한다.
- 첨부에 적힌 서비스명·가격·수치도 §6.3 벤더 사전을 그대로 통과시킨다. **남의 문서에 적힌 숫자도 `[미검증]`이다.**
- 원칙 4 개정으로 `TOO_MANY_INFERRED`는 차단이 아니라 고지가 되지만, **점검 화면 최상단에 뜬다.** 첨부만 던지고 인터뷰를 건너뛴 문서는 사용자가 그 사실을 알고 뽑는다.

### Acceptance Criteria

1. PDF · 오디오 파일 · 영상 링크를 첨부하면 **1회 호출**로 해당 섹션이 `drafting`으로 전환된다.
2. 첨부 처리 후 원본 바이트는 메모리·IndexedDB 어디에도 남지 않는다.
3. 첨부에서 도출된 가정은 모두 `source: 'inferred'`로 기록된다.
4. 첨부 1건이 쓴 토큰이 헤더 누적 비용에 합산 표시된다 (FR-012).
5. 지원하지 않는 형식·한도 초과 파일은 업로드 전에 거부하고 **한도를 숫자로** 알려준다.
6. 추출 호출이 실패해도 기존 상태는 손상되지 않는다.

## B2 — FR-016 신설: 문서 보관함과 재편집

> **우선순위:** Must · **의존:** FR-010 · **서버 불필요**

### 현재 상태 (결함)

`src/storage/persist.ts`의 `STATE_KEY = 'prd-architect:state'`는 **단일 키**다.
지금 앱은 **문서를 한 개만 보관하며, 새 프로젝트를 시작하면 이전 것을 말없이 덮어쓴다.**
빌더 요청 2는 신규 기능이라기보다 **이 결함의 수정**이다.

### 저장 구조

```
prd-architect:index          → DocumentSummary[]
prd-architect:doc:<id>       → PRDState
prd-architect:session:<id>   → SessionMeta
prd-architect:apikey         → (변경 없음)
```

```typescript
export interface DocumentSummary {
  id: string;
  projectName: string;
  version: string;
  updatedAt: string;        // ISO
  turn: number;
  /** validate() 결과 — 목록에서 완성도가 바로 보인다 */
  incompleteCount: number;
}
```

### 보완 → 새 버전 (요청 2 후반부)

저장된 문서를 열어 보완한 뒤 **새 PRD를 다시 뽑는** 흐름:

- 문서를 열면 **이어서 인터뷰**할 수 있다. 첨부도 추가할 수 있다.
- 내보낼 때 `version`을 올린다 (`0.1.0` → `0.2.0`). **이전 버전은 지우지 않는다.**
- 목록에서 같은 문서의 버전 이력이 보이고, 각 버전의 산출물을 다시 받을 수 있다.

버전을 남기는 이유: 개발 AI에게 이미 넘긴 PRD가 있는데 그것이 조용히 바뀌면
"기존 내용을 뒤집는" 바로 그 문제가 문서 레벨에서 재발한다.

### 마이그레이션

`schemaVersion` 1 → 2. 기존 `prd-architect:state`가 있으면 **첫 문서로 이관**하고 인덱스에 등록한다.
`migrate()`의 기존 원칙 유지 — **절대 예외를 던지지 않는다.** 깨진 레코드는 목록에서 건너뛰고 앱은 뜬다.

### Acceptance Criteria

1. 문서를 여러 개 만들 수 있고, 목록에 프로젝트명 · 버전 · 최종 수정 시각 · **미완성 항목 수**가 보인다.
2. 목록에서 열기 · 복제 · 삭제 · 내보내기가 된다. 삭제는 되돌릴 수 없으므로 확인을 받는다.
3. 저장된 문서를 열어 보완하고 **새 버전으로 다시 뽑을 수 있다.** 이전 버전은 보존된다.
4. 기존 단일 문서 사용자가 새 버전을 열면 그 문서가 목록 첫 항목으로 보존된다.
5. 문서 하나가 깨져 있어도 나머지 목록과 앱은 정상 동작한다.
6. 전체 백업(모든 문서 JSON 한 파일) 내보내기·가져오기가 된다 — **서버 없이 기기 이전이 가능해야 한다.**

## B3 — FR-005 개정: 내보내기 전 점검 화면

> **우선순위:** Must · **원칙 4 개정에 종속** · **서버 불필요**

빌더 요청 5의 직접 구현. "문서 뽑기" 버튼을 누르면 바로 받아지지 않고 **점검 화면**이 먼저 뜬다.

```
┌─────────────────────────────────────────────────┐
│  내보내기 전 점검            12개 중 4개 미완성  │
├─────────────────────────────────────────────────┤
│  ⚠ S7 엣지 케이스가 2개뿐입니다 (권장 5개)      │
│      [지금 작성]  [건너뛰기]                     │
│                                                  │
│  ⚠ NFR에 보안 항목이 없습니다                    │
│      [지금 작성]  [건너뛰기]                     │
│  …                                               │
├─────────────────────────────────────────────────┤
│  건너뛴 항목은 문서에 '미정'으로 표시됩니다.     │
│                        [모두 건너뛰고 내보내기]  │
└─────────────────────────────────────────────────┘
```

- **[지금 작성]** — 그 자리에서 입력하거나 해당 섹션으로 점프한다. 작성하면 항목이 즉시 사라진다.
- **[건너뛰기]** — 산출물의 미정 목록에 남는다.
- **[모두 건너뛰고 내보내기]** — 하나도 안 채워도 문서가 나온다.

### Acceptance Criteria

1. 미완성 항목이 몇 개든 **내보내기가 가능하다.** 어떤 경우에도 막지 않는다.
2. 각 항목은 어느 섹션의 무슨 문제인지 사람 말로 설명된다. 규칙 코드는 부차 정보로만 보인다.
3. [지금 작성]으로 채우면 점검 화면에서 즉시 사라진다.
4. 건너뛴 항목은 **모든 산출물**(사람용·인포그래픽·AI용)에 미정으로 표시된다.
5. 미완성이 0개면 점검 화면은 통과 확인만 보여주고 바로 넘어간다.

## B7 — FR-018 플랜 게이트 ⛔ 제약 변경

> **우선순위:** Should · **서버 필요** · **Out of Scope(인증 · 서버DB · 결제) 3개 위반**

### ⚠️ 원칙 4 개정이 과금 설계를 바꾼다

1차 제안서는 과금 게이트를 **내보내기**에 두자고 했다. **그 안은 이제 쓸 수 없다.**
빌더가 "완성 안 해도 문서는 나오게 하라"고 지시했는데 거기에 결제를 걸면
품질로 막지 않겠다고 해놓고 돈으로 막는 셈이 된다. 사용자가 느끼는 건 같다 — **문서가 안 나온다.**

### 대안 게이트 (제안)

| | 로컬 (무료) | 계정 (유료) |
|---|---|---|
| 인터뷰 · 검증기 · 점검 화면 | 전부 | 전부 |
| **내보내기** | **무제한 · 전 산출물** | 무제한 |
| API 키 | BYOK (사용자 부담) | 앱 제공 (프록시) |
| 문서 보관 | 로컬 무제한 | 클라우드 동기화 · 버전 이력 |
| 자료 첨부 | 링크 · PDF 소형 | 음성 · 대용량 포함 |
| 전체 검토 모드 | 문서당 1회 | 무제한 |

**핵심: 산출물은 절대 막지 않는다.** 유료 대상은
① **키를 안 만들어도 되는 편의**(BYOK 면제),
② **비용이 실제로 발생하는 기능**(음성 첨부, 반복 검토),
③ **보관·동기화**다.

①이 가장 강하다. 실측상 최대 이탈 지점은 API 키 발급이고, 그것을 없애주는 대가로 돈을 받는 것은
사용자가 납득하기 쉽고 원가와 직결되어 정산도 정직하다.

### 원가 리스크

프록시 모드에서 한 사용자가 1시간 녹음 10건을 넣으면 그 달 그 사용자 원가가 $0.86이다.
**플랜 한도 설계가 선택이 아니라 필수다.**

## C — 확정 제약 변경 요청

### 현행 (`CLAUDE.md`)

> - 서버 DB 없음. 클라이언트 영속화만.
> - BYOK — API 키는 사용자 소유. 앱에 내장하지 않고 서버로 보내지 않는다.

### 개정안 — 폐기가 아니라 **2계층 분리**

> - **로컬 모드 (기본 · 무료):** 서버 접촉 0. 클라이언트 영속화만. BYOK. **현행 제약을 글자 그대로 유지한다.**
> - **계정 모드 (선택 · 유료):** 로그인 시에만 서버를 쓴다. 문서 동기화와 LLM 프록시.
> - 로컬 모드는 **영구히 완전 기능으로 유지한다.** 계정 없이도 PRD를 만들고 검증하고 **전 산출물을 내보낼 수 있다.**

BYOK를 버리지 않는 이유: 그것이 이 앱의 신뢰다. 로컬 모드가 살아 있는 한
"서버 없이도 완전히 동작한다"는 주장을 계속 할 수 있다.

## D — 스코프 경고 (반대가 아니라 기록)

1. 이 요청은 `CLAUDE.md`가 Out of Scope로 못 박은 4개(**인증 · 서버DB · 결제** · 웹검색) 중 **3개를 여는** 것이다.
2. **M7(실사용 검증)이 아직 미완**이다. 앱으로 앱을 기획해보지 않은 채 서버·결제를 얹으면 검증 없이 스코프만 커진다.
3. FR이 14 → **18개**. §6.4 경고선(12개)의 1.5배다.
4. **원칙 4 개정은 되돌리기 어렵다.** 한 번 "안 채워도 나온다"로 가면 다시 조이기 힘들다.
   미정 표시가 산출물에 남는 것(§A 지켜야 할 선)이 유일한 방어선이므로 이것만은 양보하지 않는다.

### 권고 순서

```
1. 원칙 4 개정 + 점검 화면 (B3)   ← 서버 X. 빌더 지시의 핵심
2. 문서 보관함 · 재편집 (B2)       ← 서버 X. 사실상 버그 수정
3. 산출물 3종 · 선택 다운로드 (B4) ← 서버 X
4. 자료 첨부 (B1)                  ← 서버 X
5. UI/UX 개선 (B5)                 ← 서버 X
6. M7 실사용 검증                  ← 1~5를 붙인 상태로 돌린다
7. 계정 + 결제 (B6·B7)             ← 여기서부터 서버
```

**1~5는 제약을 하나도 어기지 않는다.** 6까지 마치면 유료화 대상 기능이 실제로 쓸 만한지
근거가 생기고, 그 다음에 서버를 판단하면 된다.
